# AooBee 网站运营手册（人工版）

> 本手册面向**人工运营者**，把网站内容运营的四件事讲清楚：① 手动增改内容；② 如何指挥 AI 帮你运营；③ 用 Obsidian 管本地内容库；④ 内容涨到什么量级该升级管理方式。
> 给 AI 看的精确版约定在仓库根 `AGENTS.md`（AI 会话会自动读取）。两份文档同源，本手册偏"人话讲解"，`AGENTS.md` 偏"机器可严格执行的字段与纪律"。

---

# 第一部分：手动增加和修改网站内容

## 1.1 内容放哪（URL ↔ 文件映射）

| 你想发的页面 | 文件该放哪 | frontmatter 的 `type` |
|---|---|---|
| 榜单 `/best/<slug>` | `content/articles/best/<slug>.md` | `BEST` |
| 对比 `/compare/<slug>` | `content/articles/compare/<slug>.md` | `COMPARISON` |
| 编辑评测 `/review/<slug>` | `content/articles/review/<slug>.md` | `REVIEW` |
| 指南 `/guide/<slug>` | `content/articles/guide/<slug>.md` | `GUIDE` |
| 问答 `/faq/<slug>` | `content/articles/faq/<slug>.md` | `FAQ` |
| 用户点评 `/reviews/<slug>` | `content/reviews/<slug>.md` | **无 type 字段** |
| 产品页 `/<分类>/<slug>` | `content/products/<分类>/<slug>.md` | **无 type 字段** |
| 分类总览 `/categories/` | `content/categories/<分类>.md` 汇总 | — |

⚠️ **最易踩的坑**：用户点评必须放 `content/reviews/`（独立目录），**不能**放 `content/articles/review/`——两者 frontmatter 格式完全不同。简单记：
- `content/articles/review/` = 编辑写的"评测文章"（有 `type: REVIEW`）；
- `content/reviews/` = 真实用户点评（**没有 type 字段**，用 `product` 关联产品）。

## 1.2 固定分类（共 8 个，slug 不能改）

`zhuangxiu`(装修) / `jiadian`(家电) / `yuer`(育儿) / `weixiu`(维修) / `bangong`(办公) / `yanglao`(养老) / `jiaoyu`(教育) / `ai`(AI)。文章与产品的 `category` 字段必须从这 8 个里选。

## 1.3 三类内容的 frontmatter 模板（直接复制）

**文章类**（best / compare / review / guide / faq 通用，只换 `type`）：
```yaml
---
title: 标题
type: BEST            # 按 1.1 表换 BEST|COMPARISON|REVIEW|GUIDE|FAQ
category: ai          # 8 选 1
keywords: [关键词1, 关键词2]
excerpt: 一句话摘要（卡片展示用）
description: SEO 描述，≤160 字
authorName: AooBee 编辑部
publishedAt: 2026-07-31
faqItems:
  - question: 常见问题？
    answer: 回答。
related:
  - /compare/chatgpt-vs-claude
  - /ai/chatgpt
---
# 正文标题
正文用 Markdown 书写……
```

**用户点评类**（`content/reviews/`，字段不同）：
```yaml
---
title: ChatGPT 真实使用点评
product: chatgpt      # 必须 = 对应产品文件的 slug
author: AooBee 编辑部
rating: 4.7
pros: [优点1, 优点2]
cons: [缺点1, 缺点2]
summary: 一句话总评
description: SEO 描述
related:
  - /review/chatgpt-review
  - /best/ai-writing-tools-2026
  - /ai/chatgpt
---
正文……
```

**产品类**（`content/products/<分类>/`）：
```yaml
---
name: ChatGPT
description: 一句话介绍
category: ai
url: https://chat.openai.com
company: OpenAI
pricing: 免费 / Plus $20
rating: 4.8
tags: [AI, 聊天机器人]
features:
  - name: 多轮对话
    description: 基于上下文的连续对话
pros: [生态成熟, 插件丰富]
cons: [需联网, 免费版有限额]
useCases: [写作辅助, 编程]
faqItems:
  - question: ChatGPT 收费吗？
    answer: 有免费版，Plus $20/月。
alternatives: [claude]   # 可选；不填则自动取同分类评分 Top5
---
# ChatGPT
正文……
```

**分类类**（`content/categories/<分类>.md`）：
```yaml
---
slug: ai
name: AI 工具
description: 分类一句话介绍
icon: 🤖
order: 8
published: true
---
```

## 1.4 `related` 内链字段（让页面互相推荐）

- `related` 是文章 / 点评的数组字段，元素是**路径字符串**（或 `{ href, title }` 对象）。
- 只接受以下路径，写错**不会报错但被静默过滤**（等于白写，页面不显示"相关阅读"）：
  - 文章段：`/best/x`、`/compare/x`、`/review/x`、`/guide/x`、`/faq/x`
  - 点评：`/reviews/x`
  - 产品：`/<分类>/x`（如 `/ai/chatgpt`）
- 解析由代码自动完成，解析不到的目标会被过滤，**不会出现死链**。
- 产品页的"相关阅读"按分类自动聚合本类文章，**无需手写 `related`**。

## 1.5 命名与 slug

- slug 用 kebab-case 英文（会出现在 URL 里）；中文写在 `title` 即可。
- 文件名即 slug（不含 `.md`）。例如 `content/articles/best/ai-writing-tools-2026.md` → URL `/best/ai-writing-tools-2026`。

## 1.6 发布 / 修改 / 下架流程

**新增 / 修改：**
1. 把 `.md` 放到对应目录（见 1.1）。
2. 本地预览：`npm run dev` → 打开 `http://localhost:3000/<类型>/<slug>`，重点看底部"相关阅读"是否渲染。
3. 提交：`git add content/...` + `git commit -m "新增/修改 xx 内容"`。
4. **push 由你手动完成**（AI 不会也不能帮你 push，见第二部分）。
5. 线上验证：访问 URL 看是否 200、OG 分享图是否正常、sitemap 是否收录。

**下架某篇：** 在 frontmatter 加 `published: false`（推荐，保留文件可恢复）；或直接删除文件（不可恢复）。

## 1.7 常见排查

- 页面 404：检查目录放错（尤其 review 两处目录）、slug 拼错、分类 slug 不在 8 个固定值内。
- "相关阅读"不显示：多半 `related` 路径写错（被静默过滤）；用 1.4 的合法路径核对。
- OG 图异常：中文字体已进仓库，正常无需处理；若改了模板才需重测。

# 第二部分：如何指挥 AI 帮你运营

核心一句话：**网站已经有一份给 AI 看的约定文件 `AGENTS.md`，新开任何 AI 会话它都会自动读一遍并照做。** 你不需要每次重讲规则，只要说清"要做什么"。

## 2.1 你该遵守的纪律（也是 AI 会遵守的）

- **三步法（最高优先级）**：AI 在改动任何文件前，必须先给方案 → 等你看完 → 等你明确确认，才会动手。模糊的指令它会先跟你确认，不会自作主张。
- **AI 只提交、不推送**：远程仓库是 HTTPS + 凭据管理器，弹窗需要终端界面，AI 所在环境弹不出来，push 必失败。所以分工固定——AI 做到 `git commit`，**push 永远由你手动跑**。
- **不替你虚构紧迫感**：AI 不会编"不修就出事 / 丢数据"来催你；修不修、急不急以你拍板为准。

## 2.2 你可以这样给 AI 下指令（示例）

- "按 AGENTS.md 的约定，给我加一篇 维修 类的 best 榜单，对比对象用常识填。"
- "把 `content/articles/compare/xxx.md` 扩写到 1200 字，FAQ 补到 6 条。"
- "给新建的 3 篇文章互相加 related 内链，串成网状。"
- "检查全站 related 有没有写错路径的（离线扫一遍，不用构建）。"

> AI 收到这类指令后会先给方案，你确认后才落盘。机器精确版字段与纪律见 `AGENTS.md`。

## 2.3 哪些事应该你人工拍板

- 要不要 push、推到哪个远程（你手动）。
- 业务结论类：对比对象选谁、评分给多少、是否下架（AI 可建议，决定权在你）。
- 任何你拿不准的"是否紧急 / 是否必须修"——AI 只给判断，不替你定优先级。

# 第三部分：用 Obsidian 管理本地内容库

Obsidian 是管这份 Markdown 内容库最顺手的本地工具——它把 `content/` 当成一个"知识库"，frontmatter 变成可填表单，还能用图谱看内容关系。

## 3.1 建 vault

把 `D:\project\www.aoobee.com\content` 整个文件夹作为 Obsidian 的 vault（只装内容，最干净）。这个文件夹就是你的"人工可看内容数据库"。

## 3.2 开 Properties 视图

设置 → Editor → 开启 YAML frontmatter 显示为属性卡片。这样每篇内容的 `title` / `type` / `rating` 等字段会变成结构化表单，不用对着原始文本改。

## 3.3 用 Templates 插件

1. 在 Obsidian 设置里开启核心插件 **Templates**。
2. 把第一部分 1.3 的三类模板存成 `content/_templates/` 下的笔记（如 `文章-最佳实践.md`、`用户点评.md`、`产品.md`）。
3. 新建内容时，用 Templates 插件一键插入对应模板，再填字段。

## 3.4 两套"链接"务必分清（重要）

- **网站的"相关阅读"**：靠 frontmatter 的 `related:` **路径字段**驱动，跟 Obsidian 里的 `[[双链]]` **不是一回事**。
- 你在 Obsidian 里加 `[[某笔记]]` 只是方便自己看关系图，**不会**变成网站内链；要上网站内链，必须写 `related:`。
- 建议：Obsidian 里照常用 `[[...]]` 做个人知识图谱，但**发布前以 `related:` 字段为准**。

## 3.5 防破坏设置

- Obsidian 可能自动给笔记加 `aliases`、`tags` 等属性。文章类网站不读 `tags`（只读 `keywords`），一般无害；但建议在设置里关掉"自动补全 properties"，避免它把你的 frontmatter 重排导致阅读混乱。
- YAML 标准格式（含多行数组）gray-matter 都能解析，不必担心 Obsidian 把数组写成多行会出错。

## 3.6 内容巡检（Dataview）

可写简单查询做运营巡检，例如：
- 列出某分类全部文章（按 `category` 过滤）；
- 统计各类型内容数量；
- 找出 `related` 为空的篇目（需重点补内链）。

## 3.7 推荐工作流

Obsidian 写稿 / 改稿 → 确认 `related` 内链写对 → 在终端 `npm run dev` 预览 → 提交并自己 push → 线上验证。

# 第四部分：内容涨到什么量级该升级管理

你现在是 **约 66 个节点**（8 分类 + 9 产品 + 约 39 文章/点评），全部在构建时读进内存缓存，到几千个文件都毫无压力。按阶段升级，**别过早上复杂系统**：

| 阶段 | 节点量 | 管理形态 | 要做的事 |
|---|---|---|---|
| **A 当前** | 0–约 300 | Markdown + Obsidian + git | 加 `content/_templates/` 模板库即可 |
| **B 增长期** | 约 300–1000 | 同上 + **校验脚本** | 加 pre-commit / CI 校验：必填字段、related 路径存在、slug 唯一、分类合法；可按分类拆成 git 子仓库并行协作 |
| **C 多编辑期** | 约 1000–3000 | + 轻量 CMS | 非技术编辑变多时上 Decap CMS（直接编 markdown）或 Strapi（输出 markdown），保留 markdown 为源，Obsidian 仍可并行 |
| **D 规模化** | 3000+ 或多角色 / 关系查询 | 迁 **数据库** | Prisma + Postgres。注意 `src/lib/content/types.ts` 顶部已预留"对齐原 Prisma 模型字段，便于最小改动迁移"——**架构已预留**，届时 `llms.txt` / `sitemap` 改为从库生成 |

**升级信号不是"文件多"，而是这些：**
- 你开始管不过来、常写错 frontmatter / 放错目录 → 上校验脚本（B）。
- 多人并发编辑、老冲突 → 上轻量 CMS（C）。
- 需要复杂关系查询 / 角色权限 → 上数据库（D）。

**原则**：尽量长久保留"Markdown 即源"——git 版本化、AI 友好、零成本。只有出现"多人并发编辑"或"复杂关系查询"时才上数据库，绝大多数内容站到几千节点都不需要。
